# M5 minimal GCP deployment readiness

## Capability status and architecture

M1–M4 functionality is implemented and tested locally. M5 adds reviewable infrastructure code, explicit typed source schemas, a proposed workload SQL script and an approval-gated pilot plan. IaC passed offline formatting and repository policy/schema tests, but **provider-backed validation and a Terraform plan are outstanding**. It is not yet approved for deployment. No GCP project was queried, no API enabled, and no resources or paid workloads were created. Public documentation was read without project authentication.

The target comprises one STANDARD Cloud Storage bucket, one BigQuery dataset with seven tables (`curated_transactions`, `customers`, `accounts`, and the four M4 daily marts), one runtime service account and five narrowly scoped custom roles. A pre-existing provisioner account is separate. Only Storage and BigQuery are application data services; IAM is supporting control-plane configuration. No scheduler, compute service, model, dashboard, streaming pipeline or connector is added. M3 validation remains a local, manually invoked batch prerequisite. Python runs locally under an approved operator; only loading and SQL jobs would run in GCP. See [diagram](../diagrams/m5_deployment_readiness.mmd).

Use a fresh dedicated sandbox and new names; never import/adopt a populated shared dataset or bucket. Per-environment inputs live outside Git; example values are placeholders. Region is restricted to `europe-west2` for both bucket and dataset. London is listed by both services, but project/org restrictions and actual allocation remain unverified. Do not substitute `EU` for London. [BigQuery locations](https://cloud.google.com/bigquery/docs/locations) and [Storage locations](https://cloud.google.com/storage/docs/locations) describe supported geography. Check load-job co-location and quotas again before execution.

Terraform root: `infrastructure/terraform/`. Modules separate identity, storage and BigQuery. Source schemas: `infrastructure/schemas/v1/source_tables.json`; mart schemas reuse the unchanged M4 v1 definitions. Seven unpartitioned tables are intentional for the bounded 5,000-row, full-snapshot pilot; no partitioning cost claims are made. Labels identify environment, application, synthetic classification and Terraform ownership.

Both `dev.tfvars.example` and `test.tfvars.example` are placeholders. `prefix` is the base namespace (`fincrime-m5`); Terraform appends the environment to service-account/custom-role names and the dataset. The runtime account is `fincrime-m5-dev-runner` or `fincrime-m5-test-runner`. A maximum 18-character base keeps account IDs within 30 characters. Bucket names and state directories must also be distinct. The provisioner must be a separate pre-existing account in the selected project. Do not reuse older example prefixes containing an environment suffix. Terraform >=1.9 is required because input validation refers to other variables. These naming changes require replacement if an earlier design was independently deployed; no such migration is authorized.

## SQLite → BigQuery semantic review

| Concern | Tested local behavior | Proposed BigQuery behavior / required verification |
| --- | --- | --- |
| Integer precision | SQLite signed 64-bit SUM; Python reconciliation uses exact integers | INT64 sums; no FLOAT64 casts. 5,000 × maximum M2 amount 1e9 = 5e12, safely within INT64. Overflow must fail, not silently coerce. Validate load types and exact sums. |
| Currency | Every mart grain retains currency; integer minor units and separate totals | Keep STRING currency and INT64 minor units, account currency equality and exact currency exponent map. Never sum across currencies. Decimal `amount` stays canonical STRING; JPY has zero decimals. No FX. |
| Time | Canonical UTC Z strings; lexicographic min/max; `substr` date | Explicit TIMESTAMP input; `DATE(timestamp, 'UTC')`, TIMESTAMP MIN/MAX, DATE grain. Normalize returned timestamps to UTC instants before comparison. Reject invalid/fractional/offset source forms before upload; BQ parsing alone is more permissive. |
| NULLs/types | M3 disallows empty fields; SQLite source NOT NULL plus build checks | REQUIRED target fields, explicit schemas, zero bad-record allowance, no autodetect. Empty strings and SQL NULL differ. Validate blanks, nulls and CSV field counts independently. |
| Keys/joins | Source replay verifies unique keys/FKs; SQLite mart unique indexes | BigQuery constraints do not enforce grain/FK correctness. Explicit duplicate/anti-join/ownership checks and row-count gates are mandatory. |
| Empty data | Header-only marts, no aggregate group rows | GROUP BY should return no rows; SUM over no input without grouping returns NULL. Reconcile with an explicit empty map, not an invented monetary zero row. |
| Distinct/order | Exact COUNT(DISTINCT); deterministic sorted CSV exports | Use exact COUNT(DISTINCT), not approximate functions. SQL tables have no row order; sort by the complete grain for canonical comparison. Do not sum distinct active entity metrics across grains. |
| Reconciliation | Row/count/minor-unit equality per currency; hashes for local bytes | Compare logical typed rows, not database/export byte hashes (different formatting/order). Capture cloud export hashes separately. First/last timestamps and every group must agree after type normalization. |
| Schema/write lifecycle | M4 executes CTAS and indexes in a fresh SQLite file | Terraform creates REQUIRED schemas. New proposed `infrastructure/sql/marts.v1.insert.proposed.sql` uses explicit-column INSERT plus four DELETEs in a transaction. Runtime cannot CREATE tables. Rollback behavior and script estimates remain untested. |
| String comparison | SQLite defaults to binary text comparison; M2 identifiers/categories use constrained ASCII | Preserve case and exact STRING bytes; no trimming, lowercasing, locale collation or Unicode normalization. Future non-ASCII identifiers require a new compatibility review. |
| Casts/arithmetic | M3 validates decimal strings and types before inserting into SQLite; SQLite type affinity is more permissive than a rigid schema | BigQuery is statically typed. Use explicit schemas and fail invalid casts; never use SAFE_CAST/COALESCE to hide invalid money/keys. No floating-point division, rounding or implicit coercion is needed by these four products. |

The reviewed contracts are `ingestion/foundation/contracts.py` (`CURATED_FIELDS`, entity fields, lineage), M2's currency/exponent and UTC validators, and `analytics/contracts.py` (`COLUMNS`, `GRAINS`). The M4 SQLite source database stores only `amount_minor` as INTEGER; `source_row` is TEXT there, while the proposed cloud schema deliberately uses INT64 for that numeric lineage field. All six supported currencies remain explicit (GBP/USD/EUR/SGD/AED exponent 2; JPY exponent 0). Beneficiary/device validation remains in local M3; those dimensions and M2 outcome labels are deliberately absent from the seven-table pilot. No amounts represent balances, revenue or settlement outcomes.

BigQuery integer and timestamp semantics are described in [GoogleSQL data types](https://cloud.google.com/bigquery/docs/reference/standard-sql/data-types). Local M3 inputs and schema order are pinned; M4 contracts and SQL are preserved. M5 GoogleSQL is still a proposal and has not been parsed or executed by BigQuery.

## Identities and permissions

Authentication must use short-lived ADC with impersonation of the pre-existing provisioner; provider configuration contains only its email. Separately approved workload calls impersonate the runtime account. No keys, credentials, login flow, external identity provider or secret store is added. A security administrator must authorize each operator's token-minting access on the relevant account (for example an account-scoped custom role containing `iam.serviceAccounts.getAccessToken`); never grant operators project-wide impersonation. Revoke time-limited access after the pilot. See [service-account impersonation](https://cloud.google.com/iam/docs/service-account-impersonation).

| Runtime custom role | Binding scope | Exact permissions |
| --- | --- | --- |
| jobs | selected project only | bigquery.jobs.create; serviceusage.services.use |
| objects | dedicated bucket only | storage.buckets.get; storage.objects.create/get/list |
| readers | each of the three input tables | bigquery.tables.get/getData |
| tables | each of the four mart tables | bigquery.tables.get/getData/updateData |
| metadata | dedicated dataset only | bigquery.datasets.get |

The runtime cannot change schema or IAM, create resources, delete storage objects, or provision services. Initial CSV loads use a separately approved short-lived provisioning/load phase, not this runtime role: Google documents table create/update permissions for load jobs. Do not widen the runner to cover those permissions. Data write access can still erase/replace table contents through DML; workload approval must explicitly cover replacing the four pilot marts. Read access covers only this dedicated synthetic snapshot. The runtime has no write permission on the three inputs. Custom-role permission support, CLI metadata needs and effective inherited access must be tested after approval; do not resolve errors by granting Editor, Owner, BigQuery Admin or Storage Admin. [BigQuery IAM reference](https://cloud.google.com/bigquery/docs/access-control).

The bucket and dataset use **authoritative resource IAM policies** containing only the runner's scoped role. This removes resource-local default legacy grants. It does not remove project/folder/org inheritance. Authoritative policies can remove existing access, hence fresh resources only. The project jobs grant and table grants are additive. Do not configure dataset `access` blocks alongside the dataset IAM policy; they conflict per the [provider's dataset IAM documentation](https://raw.githubusercontent.com/hashicorp/terraform-provider-google/v7.31.0/website/docs/r/bigquery_dataset_iam.html.markdown).

The provisioning identity is bootstrapped outside this configuration, with a time-limited project custom role. The exact expanded candidate is [provisioner.role.json](../infrastructure/iam/provisioner.role.json); it is a review artifact and is not consumed by Terraform. Candidate permissions for review are below; no bootstrap role is applied by this repository:

- Project metadata/IAM: `resourcemanager.projects.get`, `resourcemanager.projects.getIamPolicy`, `resourcemanager.projects.setIamPolicy`, `serviceusage.services.use`.
- Custom roles: `iam.roles.create/get/list/update`; service accounts: `iam.serviceAccounts.create/get/list/update` (no key creation or token minting).
- Storage resource management: `storage.buckets.create/get/list/update/getIamPolicy/setIamPolicy` (no object data permissions by default).
- BigQuery resource management: `bigquery.datasets.create/get/update/getIamPolicy/setIamPolicy`; `bigquery.tables.create/get/list/update/getIamPolicy/setIamPolicy` (no table data access or job execution by default).

For the initial load phase only, explicitly approve the provisioner's temporary binding to the existing jobs custom role (project), objects role (bucket), and tables data role (three input tables). Its reviewed provisioning role supplies table create/update permissions; the three data-role bindings permit loading/verification. Revoke these temporary data/job grants before runtime mart execution; they are not default Terraform grants. Initial loading therefore has a larger, time-limited permission surface. The [CSV loading reference](https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-csv) documents required permissions; verify them with approved job configurations before any cloud readiness claim.

These are permission names grouped by common prefix, not literal slash-separated permissions for a custom-role file. A bootstrap reviewer must verify provider/API calls and assign only the exact expanded permissions needed. Creation requires some project-scoped rights; name conditions do not safely constrain all create operations. Project IAM policy write access is privileged and can enable escalation; limit its time window and audit changes. It is not granted to the runner. Deletion is absent from the default candidate; [cleanup.role.json](../infrastructure/iam/cleanup.role.json) is a separate six-permission add-on requiring Gate D approval and appropriate scopes. Terraform guards prevent ordinary planned destruction; they do not protect against direct administrative API calls. Do not claim a security boundary against an administrator able to change IAM.

## Implemented offline reconciliation

`financial_crime_ml.deployment.reconcile` compares seven locally acquired CSV files to a replay-verified M3 source and a hash-verified completed M4 run. It checks exact header order, required values, INT64 range/precision, unique source keys/mart grains, every field in every row and per-currency counts/minor-unit totals. DATE values stay ISO dates; explicit timestamp zones normalize to whole-second UTC instants, including BigQuery's ` UTC` and zero-fraction formats. It rejects floats/scientific notation, fractional instants, naive times, missing/extra tables and tampered reference artifacts. Row order may differ. Empty snapshots remain empty. No cloud SDK, API calls, downloads or filesystem writes occur.

```sh
# Local only; exports must already exist. Redirect stdout to an approved evidence file if needed.
PYTHONPATH=src python3 -m financial_crime_ml.deployment.reconcile \
  --source-run outputs/runs/APPROVED-M3 \
  --reference-run outputs/runs/APPROVED-M4 \
  --export-dir outputs/runs/APPROVED-EXPORTS
make gcp-offline-check
```

Export filenames: `curated_transactions.csv`, `customers.csv`, `accounts.csv`, `transaction_daily.csv`, `customer_daily.csv`, `account_daily.csv`, `operations_daily.csv`. Headers follow the target JSON schema order exactly. Export all pages and columns; preserve STRING values without coercion. The helper refuses over 5,000 curated transactions or over 100 MiB exported CSVs. These local checks do not enforce cloud spend/upload limits. CSV matches **do not prove cloud execution or export provenance**: bind the input/export hashes to approved job IDs, schema metadata and acquisition records separately. Manifests provide integrity, not authentication. The helper reports `cloud_execution_verified=false`, even when values match.

## Cost and retention safeguards

`infrastructure/pilot_controls.json` records proposal limits: 5,000 transactions; 10 MiB total upload; 100 MiB retained across object versions; 100 MiB maximum query bytes billed; at most 20 jobs per approved execution; 10 GiB monthly query allowance; a 24-hour pilot and a day-seven storage review. These are review/future-executor controls, **not enforced by Terraform or IAM**. No cloud executor is implemented. Before running, an operator must check actual object bytes, job settings and cumulative usage; stop rather than increase limits on failure. BigQuery dry-run estimates and explicit `maximum_bytes_billed` are required; LIMIT does not bound scanned bytes. Multi-statement scripts require statement-level review and post-run child-job accounting, not trust in one script estimate. [Cost controls](https://cloud.google.com/bigquery/docs/best-practices-costs).

Propose a US$5 monthly project-filtered alerts-only budget, with 50%, 90%, 100% actual and 100% forecast alerts to confirmed billing recipients. A billing administrator must create and test it separately; no budget API/resource or notification service is provisioned. **Budget alerts are not automatic spending caps**, can arrive late, and do not stop jobs. No automatic billing-disable workflow is proposed. [Billing budgets](https://cloud.google.com/billing/docs/how-to/budgets).

Public pricing and location pages were read again on 2026-10-30 without project authentication. Both list London. The pricing pages describe on-demand query/storage charges, operation charges and free allowances; dynamic regional selectors do not establish a verified London quote. Regional storage, operations, egress, currency/taxes and shared free-tier eligibility still require manual verification. [BigQuery pricing](https://cloud.google.com/bigquery/pricing), [Cloud Storage pricing](https://cloud.google.com/storage/pricing). BigQuery's published minimum is 10 MB processed per referenced table/query, with MB rounding; small row counts alone do not eliminate query charges. Include verification queries, DML child statements, evidence versions, failed retries and delayed deletion in the cost review. A LIMIT clause is not a scan cap.

Illustrative planning assumptions, **not verified regional quotes**: US$10/TiB queries, US$0.05/GiB-month for either storage service, US$0.01/1,000 class-A and US$0.001/1,000 class-B object operations. At 10 GiB queried/month, 1 GiB BigQuery storage, 100 MiB total versioned Storage, 100 class-A/100 class-B operations, the arithmetic is about US$0.16/month before transfer, tax and other account activity, without free allowances. Reserve US$1 for this bounded pilot and retain the US$5 alert budget; this is no price guarantee or cap. Reprice and obtain approval before any billable action.

The bucket has uniform access, public-access prevention, versioning, seven-day soft delete, Google-managed encryption, no locked retention, no destructive lifecycle rules and `force_destroy=false`. The dataset/tables and bucket have Terraform prevent-destroy; tables also enable deletion protection. There are no automatic table expirations. These choices protect evidence but retain chargeable versions indefinitely until reviewed. Observe all generations and soft-deleted bytes during cost review. Encryption with customer keys and network perimeters would require a separately approved design.
